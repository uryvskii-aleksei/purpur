# Работа над проектом

## 1. Устройство репозитория

| Каталог | Назначение |
| --- | --- |
| `apps/site/public/` | Публикуемые исходники сайта, изображения, видео и лицензии шрифтов |
| `apps/site/tests/` | Проверки корзины, фильтров, доставки и целостности каталога |
| `.agents/roles/` | Канонические обязанности ролей |
| `.agents/skills/` | Навыки и подробные процедуры |
| `.agents/hooks/scripts/` | Хук форматирования и его тесты |
| `.codex/`, `.claude/`, `.cursor/` | Адаптеры сред |
| `docs/` | Документация и согласованные техпроекты |
| `scripts/` | Инструменты локальной разработки |

## 2. Проверки

```sh
npm test
npm run check
npm run test:site
npm run test:harness
```

`npm test` запускает оба набора. Тесты не требуют доступа к магазину или сторонним сервисам. Они проверяют расчёты по сохранённому каталогу, а не актуальность цен на сайте фабрики. `npm run check` проверяет синтаксис JavaScript. Для изменений интерфейса дополнительно проверьте браузером каталог, выбор оформления, корзину и подготовку заявки на широком и узком экранах.

CI в `.github/workflows/checks.yml` запускает те же проверки на Linux и Windows. Локально прошедшая проверка не означает, что CI уже завершился.

## 3. Ветки и доставка

Базовая ветка — `main`. Ветки: `feature/<id>-<slug>` и `bugfix/<id>-<slug>`, без ID, если задачи с номером нет. Например, `feature/site-order-api`. Перед новой веткой обновите базу, не затрагивая чужие изменения. Первый импорт в пустой репозиторий можно сохранить непосредственно в `main`.

В PR кратко укажите цель в `## Цель` и изменения с проверками в `## План`. Пункты отмечаются после отправки соответствующего кода. Не смешивайте стороннюю работу с задачей. Не делайте force push, merge или удаление веток без соответствующего запроса.

## 4. Исследование и решения

Небольшие понятные изменения не требуют отдельного исследования. Для существенных вариантов решения сначала подготовьте техпроект с требованиями, доказательствами, альтернативами, рекомендацией, контрактами и ограничениями. Сохраняйте его в `docs/techprojects/<slug>/<slug>.md`. Человек одобряет конкретную редакцию. После этого подготовьте декомпозицию и передачу контекста. Реализация начинается по отдельному запросу.

При работе по явно выбранной TFS-задаче исследовательская PBI может быть основным местом хранения. Не создавайте второй независимый источник того же решения. GitHub-задачи и PR не должны порождать обращения к TFS.

## 5. Изменение агентской обвязки

Общие требования меняются в `AGENTS.md`, обязанности — в `.agents/roles/`, процедуры — в `.agents/skills/`. Затем обновляются затронутые указатели и описания в адаптерах. Проверяйте относительные ссылки, соответствие имён и описаний, JSON/TOML и тесты изменённых скриптов. Пользовательские конфигурации, учётные данные и настройки интеграций не переносятся.

## 6. Следующий продуктовый шаг

Текущая версия сайта — отправная точка. Очередь улучшений и реальные ограничения перечислены в [плане развития](site-roadmap.md). Перед подключением серверной отправки заказов нужно согласовать контракт заказа и систему, принимающую заявки.
