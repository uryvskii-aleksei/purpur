# Create scoped PBIs and Tasks

Use only for creation or decomposition within the authorized assignment. Follow the [research workflow](../../design-and-docs/references/research.md). Research PBIs and Spike Tasks may be created before design approval. In that workflow, form the implementation plan and create or update implementation PBIs and Tasks only after direct human approval of the technical design. A draft-only request returns proposed payloads and links without creating items. Preparing decomposition does not start implementation or authorize closure.

1. Read the source item, design and relevant siblings. Reuse matching PBIs and Tasks. Preserve manual content and unrelated work.
2. For research, create or reuse the PBI `Исследование: <тема>`. For a source Feature, establish and verify the [PBI hierarchy](links-and-writing.md#pbi-hierarchy-under-a-feature). Its `System.Description` holds the canonical [technical design](../../design-and-docs/references/technical-design.md) and research conclusions. Create bounded research questions as `Spike: <вопрос>` Tasks under it, with the question, evidence to obtain and completion criterion. Maintain their evidence and conclusion under [work-result rules](links-and-writing.md#maintained-work-results). Keep this PBI dedicated to research, with only Spike or other research Tasks beneath it.
3. After design approval, create one or more separate implementation PBIs or reuse compatible existing implementation PBIs. For Feature research, attach them as Children of the same source Feature under the PBI hierarchy procedure. Never repurpose the research PBI or put implementation Tasks directly under it. Each implementation PBI owns its Tasks and references the research design. Choose PBI boundaries by independent business value. A useful result that can be demonstrated on its own is a candidate PBI. One PBI may span repositories. Do not split only by repository, frontend versus backend, technical layer or files.
4. Use the smallest useful set of cohesive implementation Tasks with outcomes, acceptance/checks and dependencies. Each Task is one PR-sized deliverable with a verifiable result. Split for an independent result or a meaningful responsibility, dependency or verification boundary, not for every component, hook, file or step. Do not impose arbitrary Task counts or automatically add QA, documentation or analysis Tasks merely to represent workflow stages. Preserve existing manual Tasks. For Frontend Tasks, use `Frontend: <что>`, recognizing legacy `Front:`.
5. Record approval provenance once in the research PBI under [human review and handoff](../../design-and-docs/references/technical-design.md#human-review-and-handoff). Decomposition within its approved scope needs no second human approval. If decomposition reveals a material design change, follow the amendment flow there before dependent decomposition.
6. Resolve project, area/iteration and assignee from the request or team conventions. Use the actual permitted parent under the [relation boundaries](links-and-writing.md#relations). Never create Features or Impediments.
7. Resolve initial states from the live type/project workflow under [states](states.md). Add needed [dependencies](links-and-writing.md#relations). Immediately re-read existing mutation targets, use a revision guard where actually supported and read back IDs, fields, parent and relation direction.
8. Report created/reused item links, dependencies, approval provenance and open decisions. Keep research results and the technical design in the research PBI for review. After design approval, record decomposition and the implementation handoff there, then finish the research chat. A no-go decision creates no implementation items. Do not start repository implementation there.

## Descriptions

- Start an implementation PBI with the user value and chosen approach, then link the design and source item. Keep acceptance criteria observable.
- Describe each Task through its result and checks, with a link to the design instead of repeating it. Add a start condition only when a real prerequisite prevents work.
